# WADash — WhatsApp Bot + Dashboard

A WhatsApp automation bot (Baileys) paired and operated through a Telegram console, with a React dashboard for monitoring messages, auto-replies, broadcasts, scheduled statuses, and group moderation. The bot answers 200+ chat commands across 19 menu categories.

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server (port 5000)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- Required env: `DATABASE_URL` — Postgres connection string; `CLERK_SECRET_KEY` + `VITE_CLERK_PUBLISHABLE_KEY` (and prod-only `VITE_CLERK_PROXY_URL`) for dashboard auth — managed by the Clerk whitelabel setup, do not hand-edit

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5
- DB: PostgreSQL + Drizzle ORM
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)

## Architecture decisions

- **Telegram-based pairing.** WhatsApp is paired/operated from a Telegram bot (long-polling over `fetch`, no third-party Telegram lib). Admin is trust-on-first-use: the **first Telegram account to message the bot auto-claims admin** and the bot locks to it. Set `TELEGRAM_ADMIN_CHAT_ID` to hard-lock admin and disable auto-claim.
- **Force-join channel.** Using the Telegram pairing console requires being a member of a configured Telegram channel (`@CyropesTriks`; env `TELEGRAM_FORCE_JOIN_CHAT`). The gate uses `getChatMember`, which **only works if this bot is an admin of that channel** — otherwise Telegram returns "member list is inaccessible" and the check is inconclusive. The design deliberately **fails open** on inconclusive checks (the gate allows; the leave-sweep never disconnects) so a setup mistake can never lock everyone out. Verification is best-effort/eventually-consistent: a user who leaves the channel is disconnected within one sweep interval (~5 min), not instantly.
- **Owner model.** The account that pairs becomes the owner (auto-set `ownerNumber`); `fromMe` messages are always treated as owner so the owner can self-command. `mode` (public/private) is stored in `bot_config`.
- **Per-user dashboard auth (multi-tenant).** Each dashboard user signs in with Clerk and sees ONLY their own tenant. The tenant id is always resolved server-side from the verified Clerk session (`user_links`) and attached as `req.tenantId` — it is NEVER read from the client. Users link their Clerk account to a tenant with a one-time code from the Telegram `/link` command (random, single-use, ~10min, sha256-hashed in `link_codes`). All data routers sit behind `requireAuth, requireTenant`; `/link` sits behind `requireAuth` only; health is public.
- **Command coverage.** ~200+ commands across 19 categories live in `menu-data.ts`. Implemented commands run; recognized-but-unimplemented ones reply "not yet available" (most need API keys); unknown commands are ignored silently.
- **Anti-link runs before command dispatch** so links hidden inside commands or media captions are still moderated; it only deletes when the bot is a group admin.
- **Group metadata is cached** (60s TTL, invalidated on group/participant updates) to avoid a metadata fetch per message.

## Product

- Pair WhatsApp via Telegram (`/pair`, `/qr`, `/status`, `/disconnect`) — first account to message the bot becomes admin.
- Force-join channel: users must join the Telegram channel `@CyropesTriks` before they can pair; if they later leave, the bot automatically logs out their WhatsApp connection (and DMs them to rejoin). Requires the bot to be an admin of that channel to verify membership.
- Respond to 200+ WhatsApp chat commands (menu, fun, games, tools, group admin, settings, owner, translate, etc.).
- Group moderation (anti-link), auto-replies, broadcasts, scheduled statuses.
- Anti-delete (`.antidelete on/off`, default on): deleted-for-everyone messages are sent to the owner's own number (self-chat) as a formatted `🚨 DELETED MESSAGE!` report (chat name, sender, time/date sent, who deleted, and the message text); media is forwarded too. Times render in `EAT` by default — change `ANTIDELETE_TZ` in `whatsapp.ts` for a different timezone.
- Anti–view-once (`.antiviewonce on/off`, default on): received one-time photos/videos/voice notes are auto-forwarded to the owner's own number.
- Anti-bug (`.antibug on/off`, default on): incoming crash/"bug" payloads (oversized text, or zalgo / zero-width / bidi-control character floods designed to freeze WhatsApp) are detected and dropped before any processing. In groups, on a clear malicious signature, the message is deleted and the sender removed when the bot is a group admin. A long but legitimate plain-text paste is only ignored — never grounds for a kick.
- Anti-badword (`.antibadword on/off`, default OFF, group admin-only): when a group member sends a banned profanity word, the bot deletes the message and removes (kicks) them immediately with no warning. The bot's own account, the configured owner, and group admins are always exempt, and the bot only acts when it is itself a group admin. Word list + matching live in `whatsapp.ts` (`BAD_WORDS`/`BADWORD_REGEX`, whole-word `\b` matching so compounds like "class"/"peacock" don't trigger); `enforceAntiBadword` runs in the `messages.upsert` loop right after anti-link.
- Anti-status (`.antistatus on/off`, default OFF, group admin-only): when a member shares their WhatsApp status into a group (the "mention this group in my status" feature, delivered as a `groupStatusMentionMessage`/`statusMentionMessage`), the bot deletes it immediately with no warning. Same exemptions as the other group controls (bot account, configured owner, group admins) and only acts when the bot is itself a group admin. `enforceAntiStatus` runs in the `messages.upsert` loop after anti-badword and is intentionally NOT gated on message text (status shares carry no body).
- Extra commands (latest build, mostly key-free): `.fancy` (~50 text styles), fun meters (`.simp`/`.iq`/`.pp`/`.single`/`.couple`), finance (`.convert` currency + `.crypto`), `.qr`, native `.poll`, `.urban`/`.github`/`.country`/`.npm` lookups, sticker tools (`.emojimix`/`.take`/`.tomp3`), interactive games (`.hangman`/`.tictactoe`/`.wordchain` — reply with bare moves), `.warn`/`.warns`/`.resetwarn` (3-strike auto-kick), `.autoreact on/off` (default OFF), scheduled group `.openin`/`.closein`, and reminders (`.remind 10m text`, `.reminders`, `.cancelreminder <id>`).
- Newest wave (key-free): `.afk`/`.away`/`.brb` (auto-announces when you're @tagged while away, welcomes you back on return), `.vcf` (group admin-only — export the group's members as a downloadable contacts file), `.recipe` (cooking recipes), `.pokemon` (Pokédex lookup), `.mock` (sPoNgEbOb text), `.reversetext`.
- Latest group-admin batch: `.del` (reply to a message + `.del` → bot deletes it; needs bot admin), `.kickall` (owner-only — remove all members except bot/owner/creator), `.alldemote` (owner-only — demote all admins except bot/owner/creator), `.antidemote on/off` (default OFF — if any admin other than the group creator/bot owner demotes an admin, the bot posts the reason then kicks the demoter; enforced BOTH on the participants-update event AND inside the `.demote` command so it can't be bypassed via the bot), `.setleft` (alias of `.setgoodbye`). `.add` now reports the real result and, when a direct add is blocked by the target's privacy, DMs them the group invite link instead of falsely reporting success. `.tts`/`.say` mp3 fallback is now sent as a normal audio attachment (`ptt:false`) so it still plays when opus transcoding is unavailable.
- Report-a-scammer (`.report`, aliases reportscam/reportscammer/scammer/blockscammer; undo `.unreport`/unblockall): owner-only. WhatsApp has no real bot "report" API, so the bot **blocks** the target instead. For the **global operator** (the primary/legacy tenant owner, or any number in optional env `GLOBAL_OWNER_NUMBERS`) `.report` blocks the scammer on **every WhatsApp number currently linked to the bot** (all sessions) and replies with an `ok/total` count; any other tenant owner only blocks on their own number (no cross-tenant reach). Targets resolve via reply/@mention/typed-number and are normalized to a portable phone JID — a group-reply `@lid` that can't be mapped to a phone is blocked on the current session only (the fleet-wide path requires a phone number).
- Dashboard to monitor connection status, message log, auto-reply rules, broadcasts, scheduled statuses, and groups — each user signs in with Clerk and sees only their own WhatsApp tenant, linked via a one-time `/link` code from Telegram.
- Browse captured deleted & view-once messages in the dashboard ("Captured Messages") with filters (type, chat, sender, date) and inline view/download of recovered media.

## Gotchas

- Use Baileys' `WAMessage` type (not `proto.IWebMessageInfo`) for command/message objects, or `downloadMediaMessage` and `sendMessage({ quoted })` reject them on `key` being optional.
- Never use `console.*` in server code — use `req.log` in handlers and the singleton `logger` elsewhere.
- When overriding react-query options on a generated Orval hook (e.g. `refetchInterval`), you must also pass `queryKey: getXxxQueryKey()` — the generated `query` option type requires `queryKey`.
- Telegram admin is trust-on-first-use: the first account to message the bot auto-claims admin (stored in `bot_config.telegramAdmin`). To re-pair from a different Telegram account, clear that key or set `TELEGRAM_ADMIN_CHAT_ID`.
- Force-join only actually **enforces** once the bot is an **admin of the force-join channel** (`@CyropesTriks`). Until then, `getChatMember` returns "member list is inaccessible", the check is inconclusive, and (by design) the gate lets everyone through and the sweep disconnects no one. So if force-join "isn't working", the first thing to check is that the bot was added as a channel admin. Disable the whole feature by setting `TELEGRAM_FORCE_JOIN_CHAT=""`.
- Telegram pairing uses long-polling (`getUpdates`) and must run as a **single instance**. Telegram allows only ONE active `getUpdates` per bot token, so two pollers (e.g. a running dev workspace AND the published app) return HTTP **409** to each other and starve — the bot goes silent / "stops working". To prevent this, `startTelegramBot` (`telegram.ts`) **gates polling to the deployed instance**: it only starts the poll loop when `NODE_ENV === "production"` or `REPLIT_DEPLOYMENT` is set. So the dev workspace does NOT poll by default (it logs "Telegram polling disabled on this instance"); the published app is the sole poller. Override per-instance with env `TELEGRAM_POLLING=1` (force on) / `TELEGRAM_POLLING=0` (force off) — but **never run two pollers on one token at once**. To test the bot from the dev workspace, set `TELEGRAM_POLLING=1` here AND stop/`disconnect` the deployment first. The poll loop now also logs + backs off (10s on 409) on a not-ok `getUpdates` instead of silently hot-looping. It dispatches each update through a per-chat promise chain (ordered within a chat, concurrent across chats) so one user's multi-second `/pair` never stalls other users; keep the single poll loop / single offset. Offset advances before the handler finishes = intentional at-most-once (a crash mid-`/pair` can drop that update). A self-healing safeguard also elects a single poller via a Postgres advisory lock (`acquireAdvisoryLock` in `lib/db`): among env-gated instances only the lock holder polls, standbys take over if it dies, and a demoted instance aborts its in-flight `getUpdates` + epoch-guards results so it stops 409-ing the new holder. The lock only coordinates instances on THIS code + same DB — an old duplicate deployment still must be stopped manually.
- Pairing-code linking (`/pair`): two non-obvious failure modes where a code is issued but WhatsApp won't link. (1) `requestPairingCode` does NOT stop Baileys' parallel QR timer — at `qrTimeout` (default 60s) the unpaired socket closes and is reconnected as a *new* socket, voiding the code; we set `qrTimeout: 120_000` in `makeWASocket` to widen the window. (2) `requestPairingCodeForTenant` must NOT call `requestPairingCode` when the session is already `connected` or `creds.registered` (it mutates live auth creds and returns an unusable code) — it throws `ALREADY_LINKED`/`ALREADY_REGISTERED`, telling the user to `/disconnect` first. `/qr` (scan) is the universal fallback and sidesteps WhatsApp's "Link with phone number instead" UI. Default Baileys browser is already `macOS('Chrome')`, so setting `browser` is NOT the fix.
- Concurrent multi-user pairing reliability: NEVER mint a pairing code on a fixed sleep after connect — under load the WS handshake outlasts it and the code is rejected. `requestPairingCodeForTenant` waits on `waitForPairingReady` (~20s) for a real readiness signal: `state==="connected"` OR (`socket` && per-session `pairingReady`). `pairingReady` is set on the RAW `qr` event in `connection.update` BEFORE the QR image renders (a render failure must not stall pairing) and reset on connect-start + close. Pair requests are serialized per tenant via a `session.pairLock` promise chain (overlapping `requestPairingCode` calls corrupt auth creds). The connection cap throws a typed `Error("CAPACITY")` (env `MAX_WA_TENANTS`, default 50) mapped to 503 / "busy, try again" at every caller; `ALREADY_*` → 409. `getBaileysVersion()` de-dupes concurrent cold-start fetches via one shared in-flight promise. Every fire-and-forget `connectTenant(...)` must `.catch` (a thrown `CAPACITY` would otherwise be an unhandled rejection).
- Any user-supplied URL handed to yt-dlp must pass the `MEDIA_DOMAINS` allowlist in `handlers/download.ts` (not just `isPublicHttpUrl`) — yt-dlp's generic extractor follows redirects to internal hosts (SSRF). The `url-utils.ts` host guard also decodes IPv4-mapped IPv6. Don't loosen these.
- Heavy commands (downloads/ffmpeg/AI) are gated by `limiter.ts`; always `release()` the slot in a `finally`. yt-dlp/ffmpeg run via `proc.ts` (detached, SIGKILL whole group on timeout) — needed so yt-dlp's ffmpeg grandchild is also killed.
- `limiter.ts` enforces BOTH a global concurrency cap and a **per-tenant** cap (multi-tenant fairness — one tenant can't starve the global pool). The per-tenant bucket is derived by splitting the user key on the FIRST `:`, so EVERY `tryAcquire(..., { concurrency: true })` key MUST be `` `${tenantId}:${sender}` `` — a missing tenant prefix silently disables per-tenant fairness for that path. Audit new heavy-command/capture call sites.
- TheSportsDB free key `"3"` returns an **empty body** for `lookuptable.php?l=4480` (UEFA Champions League) — its new league-phase table isn't on the free tier. So `.ucl` is a fixtures/results command (`eventsnext`/`eventspastleague`), not a standings shortcut. Domestic `lookuptable` (EPL/LaLiga/Serie A) works but is capped at ~5 rows on the free tier.
- Any image URL that is **scraped or assembled from a third party** (e.g. ephoto360's `build_server + result.image`) must be downloaded via `http-utils.ts` `fetchImageBuffer` and sent to Baileys as a Buffer — never `{ image: { url } }`. Passing a URL lets Baileys fetch it server-side with no redirect/size checks (SSRF). `fetchImageBuffer` validates every redirect hop's host (pass `isAllowed`), requires `image/*`, and caps bytes. Trusted public-API image URLs (dog/cat/wallhaven/DDG) still use `{ image: { url } }`.
- Audio downloads (`.play`/`.song`/`.ytmp3`) search **SoundCloud** (`scsearch1:`), not YouTube — YouTube now blocks all anonymous yt-dlp clients from this datacenter IP ("Sign in to confirm you're not a bot"). **YouTube _video_ is ALSO fully blocked** from this host (re-tested every player client: `tv`=DRM, `ios`/`mweb`/`web_safari`=format-unavailable, `android_vr`/`default`=403), so **video-by-song-NAME is impossible** — `.ytmp4`/`.video` keep `ytsearch1:` but it's effectively dead; video only works from a pasted non-YouTube link (TikTok/IG/FB/etc.). `player_client=android` is kept as a harmless no-op for any future YouTube recovery.
- `.play`/`.song` are **interactive** (not instant audio): they resolve the track, send a card (title/uploader/duration/link), and ask the user to reply `1`/`mp3` (audio) or `2`/`mp4` (video). The reply is a *bare* `1`/`2`/`mp3`/`mp4` (NOT a prefixed command), so it's intercepted in `whatsapp.ts`'s `messages.upsert` loop by `handleDownloadSelection` **before** `handleCommand`. Pending choices live in `commands/pending-downloads.ts` (in-memory, keyed `tenantId\0chat\0sender`, 5-min TTL, single-use, MAX 500). The continuation download uses the limiter with `skipCooldown:true` (cooldown was paid when the menu was shown) but KEEPS the global + per-tenant concurrency caps (key still `` `${tenantId}:${sender}` ``). Audio always uses SoundCloud; video is only offered/works for a pasted allowlisted link (a typed name's `2` replies with a "send a link" note and keeps the pending entry).
- yt-dlp is **vendored** at `artifacts/api-server/bin/yt-dlp` as the official **self-contained PyInstaller binary** (`yt-dlp_linux`, ~39MB) and run **directly** (NOT via `python3`). Two reasons: (1) the Nix-pinned yt-dlp has a broken SoundCloud-search extractor (`No suitable extractor (Soundcloud) found for URL .../soundcloud%3Atracks%3A...`); (2) the previous *zipapp + Nix `python3`* approach loaded the Nix store's `libssl.so.3`, which was **corrupted (EIO) in the published image** so every audio command died at `fetchMeta` with an SSL `ImportError` — and **republishing did NOT clear it** (content-addressed Nix path reused from cache). The self-contained binary bundles its own CPython + OpenSSL (extracted to /tmp at runtime), so it never touches the Nix openssl. The committed binary + its executable bit survive deploys (esbuild-only prod build; `data/`/`.pythonlibs` are gitignored, `bin/` is committed). The runner in `commands/ytdlp.ts` anchors the path via `import.meta.url`. The SoundCloud extractor regresses across versions — re-verify `scsearch1:` after any bump (known-good: 2026.06.09). See `.agents/memory/ytdlp-youtube-client.md` and `.agents/memory/nix-store-image-corruption.md`.
- **ffmpeg must be a declared deploy dependency** (`replit.nix` `deps`), not just relied on from the dev runtime-path. The deployed GCE image is built from `replit.nix` only; ffmpeg is present in dev regardless but was ABSENT in production — so yt-dlp's `-x --audio-format mp3` couldn't convert and shipped the raw SoundCloud `media.m4a`, which `sendAudio` mislabeled as `audio/mpeg` → WhatsApp "this audio is not available because something is wrong with the audio file". Declaring `pkgs.ffmpeg` in `replit.nix` was NECESSARY but NOT SUFFICIENT: the published image's Nix-store ffmpeg was itself **corrupted** — every spawn died with `spawn EIO` (errno -5), so audio stayed broken in prod. Durable fix (mirrors the vendored yt-dlp): a self-contained **static** ffmpeg is vendored at `artifacts/api-server/bin/ffmpeg` (committed, own codecs), resolved via `getFfmpegPath()` (`commands/ffmpeg.ts`, anchored to `import.meta.url` → `bin/`), used at every spawn site (`.tts`/`.say` in `handlers/media.ts`, audio effects, `.tomp3` in `handlers/stickers.ts`) and passed to yt-dlp via `--ffmpeg-location` in `commands/ytdlp.ts`. Audio sends also derive mimetype/filename from the ACTUAL produced file ext (`audioMime()` in `handlers/download.ts`), never a hardcoded mp3. See `.agents/memory/deploy-system-deps.md` + `.agents/memory/nix-store-image-corruption.md`.
- Anti-delete recovers deleted messages from an **in-memory** cache (last ~800 messages, `recentMessages` in `whatsapp.ts`) — it's lost on restart and only covers messages seen since the process started; forwarding deleted **media** via `{ forward }` is best-effort (may fail if the media was already purged). Both anti-delete and anti-view-once forward to `${ownerNumber}@s.whatsapp.net`, which is the owner's self-chat (the pairing account is the owner), so "send to my own number" = the bot messaging itself.
- Dashboard tenant scoping is the security boundary: never read a tenant id from the client (`req.body/query/params`). Always use `req.tenantId` (server-derived from the Clerk session); path-id update/delete must filter by BOTH `tenantId` AND the row id/groupJid. There is deliberately no tenant id in the client API surface, which makes cross-tenant ID tampering impossible.
- Clerk's `shadcn` theme on Tailwind v4 needs all four of: `@layer theme, base, clerk, components, utilities;` declared **before** `@import "tailwindcss";`, `@import "@clerk/themes/shadcn.css";`, `appearance.cssLayerName: "clerk"`, and `tailwindcss({ optimize: false })` in `vite.config.ts` — otherwise Clerk renders unstyled.
- Dashboard routing (wouter): the authed area is mounted at `/app`, so the top-level route must be `<Route path="/app/*?">` (the same "match base + subpaths" idiom as `/sign-in/*?`) and the **inner** `Switch` routes inside `LinkedGate` must be **absolute** (`/app`, `/app/captures`) — wouter does NOT strip the matched `/app` prefix for descendants unless you use `nest`. A plain `<Route path="/app">` with inner routes `/` and `/captures` silently dumps signed-in users on `NotFound`. Nav links in `layout.tsx` are likewise `/app/...` and active-state compares them to `useLocation()` (base-relative).
- Captured media files live on disk under `artifacts/api-server/data/captures/` (the whole `data/` dir is gitignored), so they do **not** survive a deploy/redeploy or container reset — capture **rows** persist in Postgres but their `mediaUrl` will 404 once the file is gone. Deleted-message media recovery is best-effort (downloaded from the in-memory `recentMessages` cache, may already be purged); the row is still saved with text/metadata even when media can't be fetched. There is no object-storage integration wired up.
- WhatsApp auth/session state lives in `artifacts/api-server/data/wa-auth/` and is now **gitignored** (it's secret + churns every message). It was historically committed (~16k files); gitignore doesn't untrack history, so it still needs `git rm -r --cached` via the proper delegated flow. See `.agents/memory/wa-auth-secrets.md`.
- On a `connection.update` **close**, only **transient** disconnects reconnect. `DisconnectReason.connectionReplaced` (440/conflict) and `loggedOut` (401) are **terminal — never auto-reconnect** (mark the tenant disconnected and stop). Reconnecting on 440 re-enters an endless ping-pong — each reconnect kicks the other live socket off, which kicks this one off again — that hammers WhatsApp and risks a **ban**. The trigger is a second instance/device on the same `wa-auth` creds (e.g. a **deployed copy and this dev workspace both running** the same tenant); the most-recent connection wins. Transient reasons (428/408/515) still reconnect via the backoff scheduler. See `.agents/memory/whatsapp-bot-design.md`.
- Vite dev-server artifacts (`whatsapp-dashboard`, `mockup-sandbox`) can show their workflow as **FAILED with `DIDNT_OPEN_A_PORT`** while the app is perfectly healthy — Vite logs `ready`, binds `0.0.0.0:<PORT>` (verify in `/proc/net/tcp`; `ss` is broken in this sandbox) and serves 200 through the proxy (`curl localhost:80/`). The api-server (prebuilt Node bundle) is detected fine. This is a **platform supervisor port-detection issue**, not an app/config bug, and is **NOT** fixable by editing `artifact.toml` `[services.env] PORT` (the platform injects `PORT=localPort` regardless). A full repl/container restart usually clears it. See `.agents/memory/replit-vite-port-detection.md`.
- Anti-bug (`.antibug`, default ON) uses SPLIT thresholds across FOUR signals — total length, invisible/format-control + tag-char floods, zalgo combining-mark DENSITY (marks per visible base char, NOT raw count, so heavily-vocalized Arabic/Hebrew is never mistaken for a bomb), and mention-bomb count. A long-but-plain message (or a big-group tag-all) is only *dropped* (ignored from processing); the destructive *delete + kick* in groups requires a clear malicious signature and additionally exempts the bot + configured owner (LID-safe) + group admins, acting only when the bot is itself a group admin — so a legitimate long paste / tag-all is never grounds for a kick. It fails CLOSED for dropping (drops even if the `getBool` config read throws) but only kicks when the toggle is confirmed ON, so a DB blip can't wrongly remove a member. Detection scans ALL text surfaces (text + captions + buttons/list/template content + quoted message) plus mention counts; tune the `BUG_*` constants in `whatsapp.ts`. NOTE: the bot deletes-for-everyone + kicks the attacker to stop spread/repeat, but the owner's phone receives messages independently of the bot, so anti-bug reduces (cannot fully guarantee) the owner's own device never momentarily renders an incoming crash payload.
- New DB tables here must be created with raw `CREATE TABLE IF NOT EXISTS` (via the code-execution `executeSql`, matching the Drizzle schema exactly — `timestamptz`, snake_case) because `drizzle-kit push` is TTY-blocked in this sandbox (see the composite-uniques gotcha). The `warns` and `scheduled_tasks` tables were created this way in dev — **the production DB still needs both created on deploy** (push won't run cleanly there either; run the same idempotent SQL against prod).
- Interactive games (`.hangman`/`.tictactoe`/`.wordchain`) use an **in-memory** pending store (`commands/pending-games.ts`, keyed `tenantId\0chat`, TTL + size-capped) — game state is lost on restart, exactly like `pending-downloads.ts`. Game move replies are bare (not prefixed), so they're intercepted in `whatsapp.ts` messages.upsert (download-selection → game-input → auto-react → command dispatch) before `handleCommand`.
- `task-scheduler.ts` (reminders + scheduled group open/close) has an in-flight `running` guard so a slow tick can't overlap the next and double-deliver. It is NOT instance-gated, but cross-instance double-send is naturally prevented because only the instance holding the WhatsApp socket can send (others get `null` from `getTenantSocket` and leave the task pending). `cancelReminder` is scoped to `tenant + chat + kind='reminder'` so a guessed numeric id can't cancel another chat's reminder or a group open/close task.
- Warn auto-kick exemptions must be LID-safe: resolve the participant from group metadata and match the configured owner via `participantHasNumber` (not a raw JID `===`), or an owner on a `@lid` identity slips the exemption. `.warn` exempts the bot itself, group admins, and the configured owner.
