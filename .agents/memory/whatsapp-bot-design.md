---
name: WhatsApp bot design constraints
description: Multi-tenant session model, Telegram per-user pairing, anti-link ordering, and group-metadata caching for the WhatsApp bot.
---

Durable design rules for the WADash WhatsApp bot (api-server).

## Multi-tenant: one WhatsApp connection per Telegram user
The bot is multi-tenant: every Telegram chat operates its OWN WhatsApp connection. There is NO single-admin trust-on-first-use lock anymore (it was removed) — each `chat.id` maps to its own tenant row via `getOrCreateTenantByTelegramChat`, and `/pair`, `/qr`, `/status`, `/disconnect` act only on that caller's tenant.
**Why:** the product changed from a single-owner bot to a service where each user pairs and runs their own bot. A global admin lock is incompatible with that.
**How to apply:** runtime state lives in a `Map<tenantId, Session>` in `whatsapp.ts` (each Session owns its socket, auth dir `data/wa-auth/tenant-<id>/`, anti-delete cache, anti-spam tracker, presence/reconnect timers). Anything that was a module global must be per-Session. Legacy single-owner data is `LEGACY_TENANT_ID=1`; dashboard routes + the status scheduler still call facade exports that default to it. The original root `data/wa-auth/*` is migrated into `tenant-1/` once at cold boot (creds.json moved LAST so it's crash-safe/idempotent).

## Per-socket event guards + connection cap (multi-tenant lifecycle)
Each Session can reconnect, so a tenant may have a *superseded* socket still emitting events. Every `sock.ev.on(...)` handler must bail unless it is the live socket (`session.socket === sock`), or a delayed `close`/`creds.update` from an old socket will null the new connection or overwrite fresh creds. The `MAX_TENANTS` connection cap must count in-flight connects (`connecting` flag set synchronously before the first `await`), not just open sockets, or concurrent first-connects race past it.
**Why:** found in review — stale-socket events and a raceable cap are the two non-obvious multi-tenant lifecycle bugs.
**How to apply:** define `const isLive = () => session.socket === sock` in the wiring fn and guard every handler; reserve the cap slot before awaiting auth/version.

## Anti-link before command dispatch
Run group anti-link moderation BEFORE the command dispatcher short-circuits.
**Why:** the dispatcher `continue`s when it handles a message, so a group-invite link hidden inside a recognized/stub command (or a media caption) would otherwise never be scanned. Also scan image/video captions, not just conversation/extendedText.
**How to apply:** in `messages.upsert`, compute body (incl captions), run `enforceAntiLink` first for group non-owner messages, and only delete when the bot itself is a group admin.

## Group metadata caching
Do not call `sock.groupMetadata()` per message. Use a short-TTL cache (`group-meta.ts`, ~60s) shared by the dispatcher, anti-link, and message logging; invalidate on `groups.update` and `group-participants.update`.
**Why:** active groups would otherwise hit WhatsApp metadata rate limits. Also defer the fetch until a real command will actually run.

## A "restart" command must NOT exit the process
Implement the owner `restart` as a soft WhatsApp reconnect (`socket.end(...)` → existing `connection.update` close handler reconnects), never `process.exit`.
**Why:** the api-server runs under a Replit workflow that does NOT auto-restart a killed process — `process.exit` would take the bot permanently offline until a manual workflow restart.
**How to apply:** `restartConnection(tenantId)` ends only that tenant's socket; the per-Session close handler reconnects via the backoff scheduler. Guard against duplicate reconnects via the Session state (`connected`/`connecting`/`connecting` flag) checks.

## Event-author moderation has a bot-command blind spot — gate the command too
When a moderation rule keys off the *actor* of a `group-participants.update` event (e.g. antipromote: an unauthorized promotion now POSTS THE REASON FIRST, then KICKS BOTH the promoted member(s) AND the offending admin), remember that actions performed **through the bot's own command** make the event `author` the bot — so the event-level enforcement skips them. You must ALSO gate the corresponding bot command (`.promote`), or admins bypass the rule by routing it through the bot.
**Why:** caught in review — antipromote enforced on the manual event but `.promote` (adminOnly) let any admin appoint admins via the bot with no penalty.
**LID-safe destructive kicks:** for any kick list built from event participants, resolve each candidate via `findParticipant(meta.participants, jid)` and compare the RESOLVED `.id` to the bot/creator participant ids before kicking — a base-string-only protected set misses LID/phone identity variants and can kick a protected user. Keep a base-set fallback for unresolved candidates. Also build the `@mention` reason text ONLY from the JIDs actually queued into `mentions` (have the queue helper return the canonical queued JID or null), or the text @-mentions users absent from `mentions`.
**How to apply:** for any "only owner/creator may do X" rule, enforce it at BOTH the event site (backstop for manual WhatsApp actions) and the command handler (gate on the same `getBool(key, tenantId)`, allow only `ctx.isOwner` or the group creator). Compare identities LID/PN-safe via `findParticipant`/`jidBase` (compare resolved participant `.id`s), never raw JID equality.

## Multi-tenant fairness: per-tenant limiter cap + per-chat Telegram dispatch
With many tenants on one process, heavy commands and the Telegram poll loop must not let one tenant block everyone else. The heavy-command limiter (`limiter.ts`) has BOTH a global concurrency cap and a per-tenant cap, and the Telegram poll loop dispatches per-chat (ordered within a chat, concurrent across chats).
**Why:** found in review — a single global limiter let one tenant grab every slot (starvation), and a `for (const u of updates) await handleUpdate(u)` poll loop serialized ALL chats so one user's multi-second `/pair` stalled every other user's command.
**How to apply:**
- The per-tenant bucket is derived by splitting the limiter user key on the FIRST `:`, so EVERY `tryAcquire(..., { concurrency: true })` key MUST be `` `${tenantId}:${sender}` `` (a missing prefix silently disables per-tenant fairness for that path and is easy to reintroduce — sender JIDs may contain `:` but only after the tenant prefix). Audit new heavy-command/capture call sites for this.
- Telegram: dispatch each update through a per-chat promise chain (`Map<chatId, Promise>`); keep a single poll loop / single offset (single-instance requirement). Offset advances before the handler completes = intentional at-most-once (a crash mid-`/pair` can drop that update) — acceptable, not a collision/leak.

## Any per-tenant table/route must carry tenantId from day one
A dashboard-facing feature was merged with a `captures` table that had NO `tenantId` and routes that queried globally despite sitting behind `requireTenant` — a cross-tenant leak (any signed-in user could read/download everyone's deleted & view-once messages).
**Why:** `requireAuth, requireTenant` only ATTACH `req.tenantId`; they do not scope queries. A table without a tenant column cannot be scoped at all.
**How to apply:** any new table holding per-tenant WhatsApp data needs `tenantId` (NOT NULL, FK to `tenants`, indexed) and EVERY read/write must filter by server-derived `req.tenantId` (writes pass `session.tenantId`). Path-id routes (incl. media-by-id) must filter `and(eq(id), eq(tenantId))` so IDs can't be tampered across tenants; never expose `tenantId` in the client DTO.

## Runtime toggles must be wired to socket behavior, not just persisted
Settings toggles (autoread, antidelete, alwaysonline, anticall, autotyping, per-group welcome/goodbye/antispam) are stored in `bot_config` but have ZERO effect unless wired into live socket events.
**Why:** persisting a config key is invisible to the user as "working"; the value must be read at the relevant event (`messages.upsert`, `call`, `group-participants.update`, presence interval).
**How to apply:** when adding a toggle, also add its enforcement at the event site and gate it on `getBool(key)`. Bound any in-memory state (e.g. anti-delete message cache, anti-spam sliding windows) and prune stale entries.

## connectionReplaced (440) and loggedOut (401) closes are terminal — never auto-reconnect
On a `connection.update` close, reconnect ONLY transient reasons. `DisconnectReason.connectionReplaced` (440/conflict) and `DisconnectReason.loggedOut` (401) must NOT reconnect; mark the tenant disconnected and stop.
**Why:** single-instance-per-WhatsApp-account. Reconnecting after "replaced" re-enters an endless ping-pong — each reconnect kicks the other live socket off, which kicks this one off again — that hammers WhatsApp and risks a ban. The trigger is a second instance/device holding the same `wa-auth` creds, e.g. a **deployed copy and this dev workspace both running** the same tenant; the most-recent connection wins and the rest must stay down.
**How to apply:** `shouldReconnect = reason !== loggedOut && reason !== connectionReplaced`. On replaced, log a WARN telling the operator to run a single instance then `/disconnect`+re-pair the one that should own it. Keep transient reasons (connectionClosed 428, connectionLost/timedOut 408, restartRequired 515) reconnecting via the backoff scheduler. If logs ever show repeated badSession 500 / 403 / 411 reconnect loops, classify those terminal (clear auth) too — but only if actually observed.

## loggedOut (401) must DELETE the auth dir, not just mark disconnected — or it's a silent re-pair LOCK
On a `loggedOut` (401) close, marking the tenant disconnected is NOT enough: the revoked `creds.json` (with `registered: true`) stays on disk, so the next connect RESUMES that dead session — Baileys emits no `qr` and `requestPairingCode` is unreachable for already-registered creds — and the login just fails 401 again. Result: an endless `connected → logging in → Connection Failure → closed 401` loop and the user can NEVER re-pair (looks like "pairing is broken" with no obvious error). Observed in production: a tenant looped on 401 forever after its WhatsApp session was revoked.
**Why:** registered-but-revoked creds are worse than no creds — they actively block fresh pairing while looking like a normal saved session.
**How to apply:** on `reason === DisconnectReason.loggedOut` ONLY, delete the tenant auth dir (`fs.rmSync(authDirFor(tenantId), {recursive,force})`) before `markTenantStatus(disconnected)`. NEVER wipe on transient (shouldReconnect) or `connectionReplaced` (440) closes — those creds are still valid and recoverable. Also: `disconnectTenant` must clear the on-disk auth dir EVEN WHEN there is no in-memory `Session` (e.g. right after a fresh deploy, `sessions` map empty) — otherwise `/disconnect` no-ops and the stale creds survive, so the user still can't re-pair. Recovery for an already-stuck deployment: `/disconnect` then `/pair`/`/qr` (or just retry `/pair` — the first attempt clears the dead creds via the 401 path, the second pairs fresh).

## Anti-bug (crash-payload) moderation: split "drop" from "kick", and fail closed only for dropping
A destructive moderation control (delete message + remove the sender) that triggers on heuristics must separate the *ignore* decision from the *punish* decision, and must not weaponize a config/DB blip.
**Why:** crash ("bug") payloads are detected by heuristics (text length + density of combining/zero-width/bidi-control chars). A single length threshold that both drops AND kicks would kick a member for a long-but-legitimate paste; and catching a config-read failure as "disabled" would silently let a real crash payload through on a default-ON protection, while catching it as "enabled" could kick someone during a DB outage.
**How to apply:** use two tiers — `drop` (ignore/skip all processing) on a low bar (e.g. very long OR suspicious-char signature), `remove` (delete + kick) only on a clear malicious signature (extreme length OR a flood of suspicious chars), never on length-only legit text. Fail CLOSED for dropping (drop even if the toggle read throws) but perform the destructive kick ONLY when the toggle is confirmed ON. Run the check as early as possible in `messages.upsert` (before caching/dispatch/logging) and skip `fromMe`. Scan EVERY text surface a payload can hide in — conversation/extended-text + ALL captions (image/video/document/doc-with-caption) + buttons/list/template content + the quoted message — AND count `contextInfo.mentionedJid` across surfaces (a mention bomb may carry NO text), not just the shared `body` or the first matching field. Choose each signal's metric carefully: RAW count is safe for kicking on invisible/format-control + tag-char floods and on mention bombs (real text never has hundreds of zero-width/tag chars; a real group can't exceed ~1024 members), but ZALGO combining marks MUST be judged by DENSITY (marks per visible base char), NEVER raw count — a long fully-vocalized Arabic/Hebrew/Thai passage has a high mark count but LOW density, and a raw-count kick would wrongly remove that author. Kick only when the bot is a group admin and the sender is a normal member, and exempt the bot + configured owner LID-safely (`participantHasNumber`, not bare `jidBase` equality) — mirror `enforceAntiBadword`. LIMITATION worth telling the user: the bot can delete-for-everyone + kick the attacker, but the owner's phone is a SEPARATE device that receives + renders the same message independently, so anti-bug reduces spread/repeat but cannot guarantee the owner's own phone never hangs on a targeted crash payload.

## A "kick the sender" group control must exempt the configured OWNER, not just `fromMe`
Any destructive group-moderation enforcer that removes the sender (e.g. anti-badword, anti-bug) must explicitly exempt the bot's own number AND the configured `ownerNumber`, in addition to group admins — `skip fromMe` at the call site is NOT enough.
**Why:** `fromMe` is only true when the message comes from the *paired* socket. The owner can post from their own account in a group where the bot is also present; that message is NOT `fromMe`, and if the owner isn't a group admin there, a length/word heuristic would kick the owner out of their own group.
**How to apply:** inside the enforcer, load `getConfig("ownerNumber", tenantId)` + `botNumber = jidBase(socket.user?.id)` and `return false` when the sender is the owner or bot, before the admin check. The per-group toggle defaults OFF (opt-in) because the action is destructive — it's absent from config `DEFAULTS`, so `getBool` returns false until `.anti… on`.
**CRITICAL LID gap:** a bare `jidBase(sender) === ownerNumber` is NOT LID-safe. In Baileys 7 a group member (incl. the owner) often arrives with `msg.key.participant` as an `@lid` identity, while `ownerNumber` is a phone number — so `jidBase(lid) !== phone` and the owner gets kicked despite the "exemption". You MUST resolve the participant first (`senderP = findParticipant(meta.participants, sender)`) and match against its alternate identity fields via `participantHasNumber(senderP, ownerNumber)` (checks `id`/`lid`/`jid`/`phoneNumber`/`pn`), OR'd with the plain `senderBase === ownerNumber` for the non-LID case. Same for the bot-number check. `participantHasNumber` lives in `group-meta.ts` next to `findParticipant`.

## Telegram long-poll must be gated to ONE instance (deployed-only by default)
Telegram allows only one active `getUpdates` per bot token. If a running dev workspace AND the published app both poll, they return HTTP 409 to each other and BOTH starve — the bot appears completely dead (no reply even to `/start`, which is force-join-exempt).
**Why:** publishing the app while the dev workspace is also running is the common trigger — the user sees "the Telegram bot stopped working" right after a deploy. The dev poll loop historically swallowed the 409 (only `data.ok` was checked, no log) so the logs looked clean while the bot was silent.
**How to apply:** gate `startTelegramBot` so only the deployed instance polls by default — start the loop only when `NODE_ENV === "production"` or `REPLIT_DEPLOYMENT` is set (override env `TELEGRAM_POLLING=1`/`0`). The dev workspace logs "Telegram polling disabled on this instance" and skips polling AND the force-join sweep. Make the poll loop log + back off (10s on 409) on a not-ok `getUpdates`. To test the bot from dev, set `TELEGRAM_POLLING=1` and stop/disconnect the deployment first — never two pollers on one token.

## A fire-and-forget messages.upsert interceptor that emits @mentions must skip fromMe + throttle
Any `messages.upsert` interceptor that runs on every message and can SEND a message containing `@mentions` (e.g. an AFK "user is away" announce, an auto-tag) must (1) be gated on `!msg.key.fromMe`, and (2) rate-limit its announcements per (tenant, chat, target).
**Why:** the bot's own outgoing message re-enters `messages.upsert` as `fromMe`. If the interceptor re-processes it and the message mentions an away user who is still away, the bot announces again → its announce is itself a mention of an away user → infinite mention echo/loop. Separately, with no throttle a member can spam by repeatedly @-tagging an away user, forcing one bot reply per tag.
**How to apply:** call the interceptor only for `!msg.key.fromMe` messages; keep a small in-memory cooldown map keyed `` `${tenantId}:${chat}:${jidBase(target)}` `` (e.g. 60s, size-capped like the AFK store) and skip the announce when on cooldown. AFK state itself is in-memory keyed `${tenantId}:${jidBase(user)}` (lost on restart, like pending-downloads/games), auto-cleared when the user next speaks — but exclude the very `.afk`/`away`/`brb` set-command from the auto-clear (first-word check) so refreshing AFK doesn't "welcome back" then immediately re-AFK. Mention/identity matching across @lid is best-effort; auto-clear (same participant JID) is reliable.

## The env gate alone can't stop an EXTERNAL duplicate — add a DB advisory-lock single-poller election
The env gate above only stops THIS app's dev workspace from polling. It can NOT stop a second poller that lives outside this codebase — an old/forgotten deployment, or the same `TELEGRAM_BOT_TOKEN` reused in another Repl — which still 409s the live app into silence. Add a second, self-healing layer: among instances that pass the env gate, a Postgres SESSION-level advisory lock (`acquireAdvisoryLock` in `lib/db`, held on a DEDICATED `pg.Client`) elects exactly ONE active poller; standbys wait and take over automatically when the holder's connection drops (process death auto-releases a session lock).
**Why:** the outage recurred because a poller outside this codebase held the token. An env flag inside one codebase can't coordinate across deployments/Repls; a shared database can.
**How to apply:** `startTelegramBot` launches a `pollerSupervisor` that acquires the lock, polls while held, awaits `lock.lost`, then stops + re-contends. CRITICAL: a demoted instance must stop talking to Telegram IMMEDIATELY or it keeps a 30s long-poll open and 409s the new holder — tie the poll loop's lifetime to lock-hold: (1) abort the in-flight `getUpdates` via an `AbortController` on lock loss; (2) re-check `running && epoch === pollEpoch` AFTER every `getUpdates`/`drainBacklog` await, before dispatching or advancing `offset` (a long-poll can return after the lock is gone); (3) bump a `pollEpoch` each stint so a resumed stale loop exits. LIMITATION: the lock only coordinates instances running THIS code against the SAME db — an OLD deployment on pre-lock code ignores it, so a duplicate/old deployment must still be stopped manually.

## Event-only group moderation (antipromote/antidemote) is bypassable — also gate the command
A per-group control that punishes an unauthorized admin action by reacting ONLY to the `group-participants.update` event (e.g. anti-demote kicks whoever demoted an admin) can be trivially bypassed by performing that same action THROUGH the bot's own command (`.demote`/`.promote`).
**Why:** when an admin runs `.demote @x`, the bot calls `groupParticipantsUpdate`, so the resulting `group-participants.update` event has `author` = the BOT — and the enforcer (correctly) exempts the bot, so no punishment fires. Net effect: anti-demote stops a manual WhatsApp-UI demote but not a `.demote` command, defeating the feature.
**How to apply:** mirror what `.promote` already does for anti-promote — inside the `.promote`/`.demote` command handler, when the matching `antipromote:`/`antidemote:` toggle is ON, allow the action only for `ctx.isOwner` or the resolved group creator (`findParticipant(meta.participants, meta.owner)`), else refuse. Enforce at BOTH layers: the event handler (catches manual UI actions by other admins) AND the command (catches the bot-command bypass). Same lesson applies to any future "react to the event" group control.

## Per-tenant `ownerOnly` is NOT authorization for fleet-wide (cross-session) actions
A command gated only by the per-tenant `ownerOnly` flag (`isOwner = fromMe || sender===botNumber || sender===tenant.ownerNumber`) authorizes the caller for THEIR OWN tenant only. If that command then reaches across ALL live sessions (e.g. block a number on every linked WhatsApp), every tenant owner can mutate every other tenant's account — a cross-tenant privilege escalation in an app whose whole design is strict per-tenant isolation.
**Why:** `.report` (block a scammer everywhere) iterates the whole `sessions` map; `ownerOnly` does not distinguish "owner of this tenant" from "operator of the bot fleet". A code review flagged this as broken access control.
**How to apply:** any action that touches sessions/tenants other than the caller's must have a SECOND gate for a GLOBAL operator — gate on `ctx.tenantId === LEGACY_TENANT_ID` (the primary/original paired account) and/or an explicit allowlist env (`GLOBAL_OWNER_NUMBERS`, digits matched against `ctx.senderNumber`). Non-global owners should degrade to acting on their own session (`ctx.sock`) only, never fleet-wide.

## Cross-session blocking needs a portable phone JID, not an `@lid`
An `@lid` identity (common as `contextInfo.participant` on a GROUP reply) is per-account: session A's lid for a user is meaningless to session B. Calling `updateBlockStatus(lid)` on other sessions blocks nothing, yet the loop still counts ok/total as if it worked.
**Why:** the fleet-wide `.report` must reach the same human on every linked number; only `<digits>@s.whatsapp.net` is portable across sessions.
**How to apply:** normalize the target first — prefer typed digits / a DM's `@s.whatsapp.net`; for a group `@lid` try `findParticipant(...)` alt fields (`jid`/`phoneNumber`/`pn`) to recover a phone. Only call the cross-session helper with a phone JID; if it stays an `@lid`, block on the current session only and ask the operator for the number rather than reporting a false fleet-wide success.
